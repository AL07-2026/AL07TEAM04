# 공고 수집·검색 점검 결과

점검 기준: 2026-09-08 00:53 KST. `leedongwook` 브랜치와 실제 Firebase 예약 작업, 실행 로그, Firestore 생성 시각, 공개 검색 응답을 대조했다. 수집 실행이나 외부 채용 API 추가 호출, DB 수정, 공고 삭제는 하지 않았다.

## 결론

자정 예약 실행은 정상이나 신규 공고 유입은 정상 상태가 아니다. 실제 공고 문서는 9월 4일 이후 추가되지 않았고, 마감 공고는 날짜에 따라 조회 대상에서 계속 제외된다. 저장 문서 수는 16,316건으로 유지됐지만 조회 가능 공고는 9월 7일 밤 7,871건에서 9월 8일 7,389건으로 감소했다. 차이 482건은 9월 7일 마감 공고 수와 일치한다.

### 원천별 상태

- 워크넷: 9월 3일 로그에 `개인회원은 사용할 수 없는 OPEN-API입니다.` 오류가 기록됐다. DB의 worknet 출처 문서는 고정 샘플 1개뿐이다. 현재 키의 이용 자격·승인 상태를 확인해야 하며, 단순 재시도로 해결되는 오류가 아니다. 9월 4일 이후 예약 실행 완료 로그에는 워크넷 결과 항목도 없다.
- 서울시: DB 문서 14,581개 중 최신 생성 시각은 8월 18일 01:54 KST다. 최근 수신·갱신이 있었어도 신규 문서는 없었다. 원천 최신 정렬/조회 범위/데이터 자체 최신성을 확인해야 한다. 이 점검만으로 API 주소가 변경됐다고 결론 내릴 수는 없다.
- 공공채용: 마지막 신규 생성과 정상 갱신은 9월 4일 00:00 KST다. 이후 4회 연속 시간 초과가 확인됐다.
- 자동 AI 분석: 최근 모든 실행에 `Gemini API key is not configured.` 오류가 남고 분석 0건이다. 배포된 예약 함수에는 Gemini secret 연결도 없다. 공개 채용 API 자체 수집과 별개의 후처리 결함이다.

## 장애를 숨기는 상태 기록

1. 원천 오류를 catch한 뒤 `lastCompletedAt`을 갱신한다. 수집 실패 상태여도 예약 작업과 통계는 성공처럼 보인다. `functions/lib/backendAccumulator.mjs:1052`, `:1085`, `:1134`, `:1155`.
2. 고정 샘플 `WORKNET-WN-DSN-02`를 매일 갱신하고 수집 건수에 1을 더한다. 9월 5·6·8일의 `syncedThisRun:1`은 새 채용공고 유입이 아니다. `functions/lib/backendAccumulator.mjs:960`.
3. `saveSyncState(..., {merge:true})`의 중첩 데이터에 과거 성공 건수와 새 오류가 함께 남는다. 현재 메타데이터에는 public의 과거 `activeUpserts:400`과 최신 `error:Fetch timeout`이 공존한다. 시도별 결과를 교체하거나 이력 문서를 분리해야 한다. `functions/lib/backendAccumulator.mjs:672`.
4. 현재 브랜치는 수집 시작 전에 당일 날짜를 선점한다. 실패해도 당일 재시도할 수 없고 성공 기준이 아니다. `functions/lib/backendAccumulator.mjs:640`. 실제 서버 메타데이터의 날짜는 9/3에 머물러 있어 배포 버전 차이까지 고려해야 한다.
5. HTTP 상태·응답 스키마 검사가 부족하다. Worknet 파서에 502 HTML을 넣으면 오류 없이 빈 목록으로 해석되고, 서울시 RESULT 오류도 0건으로 취급될 수 있다. `functions/lib/backendAccumulator.mjs:19`, `:493`, `:1065`.

현재 브랜치의 수집 코드는 워크넷 첫 100건·서울시 첫 1,000건을 요청하지만 실제 예약 로그는 서울시 2개 구간을 읽는다. 브랜치 수정이 공통 수집 서버에 그대로 반영된 상태가 아니다. 최근 프리미엄 배포는 프리미엄 API와 미리보기 Hosting만 변경했으며, 공고 수집 감소를 직접 발생시키는 코드는 추가하지 않았다.

운영과 미리보기는 `/api/jobs/**` 및 DB를 공유한다. 공통 수집 함수를 수정·배포하면 두 화면의 공고 데이터 모두에 영향을 준다.

## 권장 수정 순서

1. 원천별 실제 배포 코드를 브랜치와 대조하고, 워크넷 키의 이용 권한을 확인한다.
2. 하루 한 번 예약은 유지하되 성공/실패를 구분한다. 요청량과 실행시간 상한을 정하고, 일시 오류에 한해 제한된 재시도를 허용한다. 과도한 호출을 유발하는 무한 재시도는 두지 않는다.
3. 최신 공고를 빠뜨리지 않도록 페이지 크기·정렬·체크포인트를 검증하고, 신규/변경/마감/실패/마지막 원천 성공 시각을 따로 저장한다. 샘플 갱신은 운영 수집 지표에서 제외한다.
4. 비공개 프로젝트 공개 검색 제외와 서버 기준 단일 집계·페이지 처리를 먼저 보강한다.
5. 실패 시 실제 이전 성공 목록과 오류 상태를 보여주고, 계정별 통계 캐시·마감 임박 계산을 수정한다.
6. AI 키 연결, 분석 대상 상태, 분석 완료 해시·처리 커서를 정리한다.

검증: 기존 전체 검사(타입·린트·48개 테스트 파일/411개 테스트·빌드) 통과. 기존 테스트가 운영 API 시간 초과와 위 엣지 케이스를 충분히 검증하지 못함을 별도 로컬 재현으로 확인했다. 이 문서는 점검 결과이며 수집 서버 복구가 완료됐다는 뜻이 아니다.
