# 공고 수집 복구 (2026-09-08)

## 확인한 원인

- 기존 운영 함수는 서울시 GetJobInfo와 공공채용을 큰 페이지로 요청하고 12초 후 중단했다. 9/5~9/8 신규 문서 유입이 0이었다.
- 같은 키로 각 5건을 조회하니 공공채용은 1.3초에 응답했고 9/8 등록 공고도 있었다. 원천 공고가 없는 것이 아니었다.
- 서울시 기존 GetJobInfo 앞 5건은 7/27 등록 건이었다. 8/21 공개된 새 recMntList는 형식이 다르고 원천 공고 ID가 없다. 새 API 처음 5건의 등록일은 8/5, 마지막 5건은 9/3이었다. 앞 페이지만 최신이라고 가정할 수 없다.
- 워크넷은 실제 개인회원 사용 제한 응답이었다. 코드를 바꾸거나 재시도를 늘려 해결할 수 있는 문제가 아니므로 원천 이용 권한 확인이 별도로 필요하다.

공식 근거: [서울시 일자리포털 채용정보](https://data.seoul.go.kr/dataList/OA-23047/S/1/datasetView.do), [공식 API 명세](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-23047&srvType=A&infSeq=2&serviceKind=1).

## 수정 범위

- 서울시 recMntList 신규 형식 대응, 2자리 연도 변환, 원천 업무·조건만 저장. 공개된 안정 필드의 복합 해시로 문서 ID 생성(행 번호 사용 안 함). 담당자 전화는 수집하지 않는다.
- 서울시 전체 건수 조회 후 끝쪽 1,000건과 순환 1,000건, 공공채용 앞 100건과 순환 100건, 워크넷 100건을 읽는다. 공식 API에 없는 정렬 파라미터는 만들지 않는다.
- 매일 00:00 KST 예약 1회 유지. 정상 시 원천 HTTP 최대 6회, 일시 실패 재시도 포함 최대 12회. 방문자 수와 무관하다. 예약 자동 재실행은 하지 않으며, 실패 후 같은 날 복구 실행은 대기시간과 일일 총 2회 상한을 적용한다.
- 권한·할당량·스키마 오류는 반복 호출하지 않는다. 응답 상태·크기·전체 시간 제한을 검사하며 키/URL/응답 원문을 오류 로그에 넣지 않는다.
- 실제 신규/변경/변경 없음/실패를 구분. 고정 샘플을 매일 덮어쓰는 코드를 제거했다. 원천 한 페이지를 성공적으로 저장한 뒤 다른 페이지가 실패해도 저장된 공고를 보존한다.
- 원천별 성공 시각과 날짜, 커서, 시도 수를 기록. 중첩 결과 맵은 교체해서 과거 성공 숫자가 최신 오류에 섞이지 않도록 한다. 전체 성공일 때만 전체 성공 시각을 갱신한다.
- 원자적 잠금과 실행 소유자 검증, 10분 잠금·540초 함수 제한·동시 실행 1개. 실패한 이전 실행이 더 새 실행 상태를 덮지 않도록 한다.
- AI 키 연결, 원천 해시와 AI 성공 해시 분리, 잘못된 결과는 실패 처리, 분석 대상을 순환 조회한다. 수집 실행 후 하루 최대 50건, API 자체 자동 재시도는 끈다. 원천 변경 시 오래된 분석 결과를 비운다.

## 배포 범위와 남은 항목

수집 예약 함수 `scheduledJobSync`만 변경한다. 운영 Hosting/랜딩/공통 조회 API/커뮤니티/프리미엄 API는 이 작업에서 배포하지 않는다. 운영과 미리보기의 공고 DB는 공유되므로 수집된 공고는 두 환경에 반영된다.

워크넷 이용 권한, 원천 제공 시차, 한정된 페이지 범위 밖 공고는 계속 확인이 필요하다. 이전 점검에서 발견된 프런트 중복 페이지 처리와 공통 API 비공개 프로젝트 필터 등은 별도 변경 대상이며 이번 수집 서버 복구와 구분한다.

## 검증

모의 원천 응답으로 HTTP/스키마/권한/재시도/시간·크기 상한, 새 서울시 변환, 당일 중복 실행 방지, 잠금 소유권, 실패 시 이전 성공 시각 보존 및 실제 신규 집계를 검증했다. 운영 배포 및 실제 실행 결과는 아래에 별도 기록한다.

### 실제 실행에서 추가 확인한 연결 문제

- 08:58 KST에 `scheduledjobsync-00030-vuy` 배포 완료. 08:59 수동 검증 실행은 09:01에 종료됐지만 원천 수집은 실패했다. 서울시와 공공채용은 각각 25초 제한으로 2회 시간 초과, 워크넷은 이용 권한 오류 1회, 실제 신규 저장은 0건이었다.
- 같은 새 서울시 요청을 이 PC에서 운영과 동일한 Node HTTP 전송 코드로 실행하면 약 130ms에 5건을 받았다. 로컬 응답만으로 클라우드 수집이 복구됐다고 판단할 수 없다.
- 운영 수집 함수의 VPC 커넥터·별도 egress·프록시 환경 설정은 없었다. 로컬 DNS에서 세 원천 모두 IPv4 주소로 조회됐다. IP 차단이 원인인지는 아직 입증되지 않았으므로 확정하지 않는다.
- 후속 보완은 IPv4 연결 명시, 수집기 식별 헤더, 비밀정보 없는 실패 단계(DNS/연결/TLS/헤더/본문)·경과 시간·수신 바이트 기록이다. 호출·재시도 상한은 늘리지 않는다.
- 전체 검증: 53개 테스트 파일, 488개 테스트, 타입 검사·린트·프로덕션 빌드 통과. 기존 번들 크기 안내 경고만 남았다.
