# 기업 회원 등록 흐름 검토 — 2026-09-08

## 결론

현재는 프리미엄 샘플 기업을 보여주고 텍스트 신청을 접수하는 단계다. 기업이 직접 사진을 올리고, 보완 요청을 처리하고, 승인 후 자사 공고로 인재를 연결하는 전체 과정은 완성되지 않았다. 실제 채용공고 등록에서도 첨부, 저장 실패 복구, 같은 제목 재등록 처리가 부족하다.

이번 작업은 검토 요청에 따른 읽기·모의 테스트다. 운영 코드 수정, 배포, 실제 신청/공고 생성, 파일 업로드, 메일 발송은 하지 않았다. 기업 계정으로 운영 DB/Storage에 저장하는 종단 간 테스트와 배포된 보안 규칙 검증은 수행하지 않았다.

## 검증 방법

- 운영 `/premium-companies` 브라우저 화면과 사진 표시 확인: 샘플 4개가 실제 표시된다. 이는 기업의 사진 업로드 성공을 의미하지 않는다.
- 실제 `App`의 `/company/projects/new` 경로를 모의 기업 계정으로 렌더링해 최종 등록 화면 확인.
- Firebase·HTTP를 격리한 진단 8개를 실행해 아래 현행 동작을 재현했다. 테스트 통과는 문제 상황이 재현됐다는 뜻이지 기능이 완성됐다는 뜻이 아니다.
  1. 프리미엄 신청 화면의 파일 입력 부재.
  2. 사진 URL/저장 경로를 보내도 신청 검증 결과에서 제외됨.
  3. `changes_requested`에서 버튼 비활성화.
  4. `rejected`에서 버튼 비활성화.
  5. 실제 공고 등록 화면의 파일 입력 부재 및 저장된 회사명 미적용.
  6. 동일 기업·동일 제목 신규 등록의 같은 ID/병합 저장.
  7. 서버 저장 실패 후 재조회 시 로컬 항목만 남고 재저장 안 됨.
  8. 서버 목록에서 없어진 항목이 로컬 캐시 병합으로 계속 남음.
- 진단 파일은 `.firebase` 아래 텍스트로 보관해 기존 타입 검사·린트·테스트에 끼어들지 않도록 분리했다.
- 최종 `npm run validate`: 타입 검사·린트·55개 파일/526개 기존 테스트·빌드 통과. 기존 번들 크기 안내 경고만 남았다. 기존 테스트가 빠진 기업 운영 시나리오는 위 8개 별도 진단으로 확인했다.

### 사진 코드가 있는데 실제 화면에는 없는 이유

`FlowPages.tsx`의 예전 `ProjectRegisterPage`에는 JPG/PNG/WEBP/PDF, 10MB·5개, 미리보기 기능이 남아 있다. 하지만 현재 `/company/projects/new`는 `App.tsx:182`에서 `/company/project-database?register=1`로 이동하며 이 예전 컴포넌트를 사용하지 않는다. 현재 통합 등록 모달에는 파일 입력이 없다. `JobDatabasePage.tsx` 내 다른 파일 입력은 지원자의 이력서 첨부이므로 기업 공고 첨부와 혼동하면 안 된다.

예전 첨부 코드도 공고를 먼저 공개 저장하고 파일을 나중에 업로드한다. 실패 시 부분 업로드 정리나 재시도 연결이 없으므로 그대로 다시 연결하는 것만으로는 충분하지 않다.

### 프리미엄 운영 연결

서버는 `premium_company_applications/{uid}`에 최초 신청을 저장하지만, 공개 목록은 별도 `premium_company_listings`의 `status: published` 데이터를 읽는다. 현재 서비스의 관리자 화면/라우트에서 신청 승인 후 공개 목록을 만드는 기능을 찾지 못했다. Firebase 콘솔 등을 통한 수동 운영 가능성까지 없다고 단정하는 것은 아니다.

신청 반환 데이터도 회사명·상태·제출 시각만 포함한다. 기존 입력 내용, 보완 사유, 사진 상태를 다시 읽고 편집하려면 API를 함께 확장해야 한다.

## 정상 동작이 확인된 기반

- 프리미엄 신청은 서버가 검증한 로그인 UID와 기업 역할을 사용한다. 제출 본문의 회사명/역할을 그대로 신뢰하지 않는다.
- 최초 신청은 트랜잭션으로 계정당 한 건을 검사한다. 이 원칙과 보완 수정은 양립할 수 있다.
- 공개 목록은 담당자 이메일 등 내부 신청 정보를 제외한다.
- 기본 공고 등록, 본인 공고 수정/삭제, 받은 제안 단계 처리는 기존 모의 테스트가 있다. 이것만으로 실제 Storage 권한·메일 도착까지 검증됐다고 볼 수는 없다.

## 남아 있는 운영 의존성

- 공통 API는 `GMAIL_APP_PASSWORD` 미등록으로 직전 배포가 보류됐다. 비공개 기업 공고 제외 보완은 `leedongwook` 코드에는 있지만 운영 공통 API에는 아직 적용되지 않았다. 다른 공개 조회 경로와 캐시까지 함께 점검해야 한다.
- 이메일 발송 완료를 보장할 수 없다. Gmail 연결 또는 발송 비활성화 후 다른 API 선배포 중 사용자 선택이 필요하다.
- 현재 공개 사진은 샘플 4장이다. 실제 기업 사진의 형식/용량/잘못된 파일/권한/네트워크 실패/저장 후 재접속/교체/삭제는 업로드 기능 구현 후 테스트 계정과 별도 테스트 공간에서 검증해야 한다.

## 권장 구현 순서

1. 공고 고유 ID·서버 저장/실패 복구·공개 여부 일관성을 먼저 보완.
2. 프리미엄 및 공고 사진 업로드를 권한·파일 검증·정리까지 포함해 구현.
3. 신청 수정·보완·승인·공개 노출·기업 공고 연결을 완성.
4. 회사 정보 자동 채움, 작성 단계, 미리보기, 초안, 제출 후 관리 화면 개선.
5. 테스트 기업 계정으로 저장·다른 기기 재조회·수정·삭제·승인·공개 노출을 검증한 후 별도 승인 범위로 배포.
