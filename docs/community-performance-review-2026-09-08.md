## 변경 전 실측

대상은 `leedongwook` 미리보기와 공유 `communityApi` 함수이다. 로그·함수 설정·공개 읽기 요청만 확인했고 게시글/회원 데이터를 변경하지 않았다.

- 배포 버전 `communityapi-00004-puv`(9/5), 256MiB, timeout 30초, 최소 인스턴스 0.
- 공개 글 목록은 **2개, 응답 1,394바이트**. 첫 요청 **2,994ms**, 이어진 요청 **218ms / 222ms**, 첫 글 댓글 조회 **227ms**.
- 최근 요청 로그: 초기 프로필 요청 약 2.50~2.75초, 초기 목록 최대 약 2.98초. 이후 댓글 요청 대부분 0.06~0.18초. 현재 지연을 글이 너무 많아서라고 설명할 수 없다.
- 첫 실행과 연속 실행의 차이는 콜드스타트의 영향이 크다는 근거다. 다만 관측된 3초 모두가 특정 라이브러리의 초기화 때문이라고 단정하지 않는다.

## 코드에서 확인한 원인과 변경

1. 커뮤니티 서버도 공통 엔트리에서 AI·수집·메일·음성 모듈을 모두 불러왔다. 새로운 `functions/entry.mjs`는 Firebase가 설정하는 `FUNCTION_TARGET=communityApi`일 때 경량 엔트리만 로드한다. 다른 함수 및 배포 discovery는 기존 전체 엔트리를 유지한다. 공통 API와 전용 API가 같은 커뮤니티 라우트 등록 함수를 사용한다. 추가 상시 인스턴스 비용은 발생시키지 않는다.
2. 로그인 목록은 게시글 → 활동명 → 공감 상태를 순차 조회했다. 게시글 이후의 활동명·공감 조회를 병렬화했다. UID 인증과 작성자 검증, 익명 표시 및 기존 조회 상한은 유지한다.
3. 재방문·동시 요청·댓글 재선택마다 같은 자료를 다시 조회했다. 현재 계정에 한정된 **20초/최대 32개 메모리 캐시**와 진행 중 요청 공유를 적용했다. 로컬 영구 저장은 사용하지 않는다. 서버가 원본이며 같은 계정의 단기 재방문만 재사용한다.
4. 글·댓글·활동명·공감 등 쓰기 전후에 읽기 캐시를 무효화한다. 다른 계정으로 전환하면 캐시와 화면 상태를 분리하고, 이전 계정의 늦은 응답 또는 쓰기 이전의 늦은 읽기 응답이 돌아와도 화면/캐시를 되살리지 않는다. HTTP 공용 캐시는 사용하지 않는다.
5. 동일한 글을 다시 누르면 댓글만 지우고 재조회는 하지 않던 버그를 수정했다. 조회 중/실패/실제 빈 상태를 구분하고 수동 새로고침과 재시도를 제공한다. 네트워크 응답은 15초 제한을 적용하되 쓰기 지연 시에는 중복 제출 방지를 위해 저장 여부부터 확인하도록 안내한다. 이 제한은 Firebase 인증 복원/토큰 획득 대기 시간까지 포함한 전체 화면 로딩 상한은 아니다.

## 검증

- 새로운 로컬 Node 프로세스 각각 3회, 네트워크 호출 없이 엔트리 import 비교: 기존 전체 경로 **854 / 836 / 832ms**, 커뮤니티 전용 경로 **756 / 733 / 726ms**. 중앙값 기준 약 12% 감소다. 이는 로컬 모듈 초기화 측정이며 운영 HTTP 전체 응답 시간이 아니다.
- 모의 지연 테스트로 활동명 조회가 끝나기 전 공감 조회 시작을 확인했다. 현재 계정별 소유권/공감 표시와 타인의 게시글·댓글 수정/삭제 거부를 실제 저장소 함수 + 메모리 DB 모형으로 검증했다.
- 동일 계정 동시 요청과 20초 이내 반복 읽기는 HTTP 1회, 만료·계정 전환·쓰기 후에는 새 요청을 만드는 것을 검증했다. 캐시 오염, 오래된 응답, 조회 실패 및 댓글 선택 회귀 테스트를 추가했다.
- `npm run validate`: 55개 테스트 파일, **525개 테스트**, 타입 검사·린트·프로덕션 빌드 통과. 기존 번들 크기 안내 경고는 별도 개선 대상이다.
